## 一、Prompt 工程与微调的边界

### 1. 核心概念澄清

#### Prompt 相关术语

| 术语 | 英文 | 含义 |
|---|---|---|
| 提示工程 | Prompt Engineering | 系统性设计提示词与调用参数，让模型稳定、可重复、规模化地输出正确结果 |
| 提示设计 | Prompt Design | 侧重沟通与表达：写清指令、设定角色、明确格式。常与 Prompt Engineering 混用 |
| 提示微调 | Prompt Tuning | 改模型内部参数的技术：训练可学习的"软提示"向量，**不是人写的文字** |
| 前缀调优 | Prefix Tuning | Prompt Tuning 的近亲，在每层 Transformer 前加可训练前缀向量 |

**关键区分：**

> Prompt Design / Engineering 是**推理时工程**（模型权重不动）；
> Prompt Tuning / Prefix Tuning 是**参数高效微调**（改内部参数，需要模型权重访问权限）。

两条线的"怎么做"：Prompt Design 直接用现成标准，见本文[第二、三章](#二co-star-框架中文版)；Prompt Tuning 的机制见下节。

#### Prompt Tuning 怎么做（机制，理解边界即可）

- **冻结全部模型权重**，只训练一组**连续向量**（soft prompt）：在输入层（Prefix Tuning 则在每层 Transformer 前）拼接可训练向量，与文字 prompt 一起送入模型。
- 训练数据就是（输入 → 期望输出）对，梯度反传只更新这些向量，模型本体不动。
- 产物是**一组数值向量**，不是文字：人读不了、改不了，也基本不能跨模型迁移。
- 前提：必须能访问模型内部计算（自部署开源模型）。在线 API 给不了这个入口——这就是它在工程实践里出场率远低于 Prompt Design 的原因。

### 2. 微调（Fine-tuning）

用数据继续训练模型、修改模型权重，让模型"内化"格式或领域知识。与推理时工程是**两条独立路线**，不是同一件事的两个阶段。

### 3. 两条技术路线

#### 路线一：推理时工程（Inference-time Engineering）——不改权重

绝大多数产品的主路线，又分两层：

**A. 纯提示层（Prompt-level，纯 API 调用可实现）**

- 系统消息硬性约束输出格式（用分隔符隔离指令与内容）
- **零样本提示**（Zero-shot）：只给指令，不给示例
- **少样本提示**（Few-shot）：在 prompt 里给 1~3 个"输入→期望输出"示例，让模型模仿
- 低 temperature / top_p，降低随机性
- API 结构化输出参数（`response_format` 设为 `json_object` 或 JSON Schema），从解码层杜绝格式错误
- 分步拆解、链式调用：把复杂任务拆成多次 API 调用，每次任务更窄

**B. 系统层（System-level，需 API 外基础设施）**

- **输出校验 + 自动重试**：应用层用 JSON Schema / 正则校验，不合规就重调并把错误反馈给模型
- **RAG**（检索增强生成）：先检索相关资料再让模型回答，减少胡编、提升事实准确率
- **上下文工程**：向量库、文档处理、查询重写、状态管理
- **Function Calling / 工具调用**：让模型调函数查真实数据，服务端需实现函数端点

#### 路线二：微调（Fine-tuning）——改权重

适用场景（**不是起点，是升级选项**）：

1. 格式极复杂，结构化输出参数搞不定
2. 领域术语/风格要求高，提示里塞示例太占 token
3. 延迟敏感，需要缩短提示
4. 厂商提供微调 API 且成本可接受

### 4. Prompt 工程内部的方法论

**按示例数量分**

- **零样本**（Zero-shot）：不给示例，只写指令
- **少样本**（Few-shot / In-Context Learning）：在 prompt 里给示例让模型模仿。纯文本操作，成本最低

**推理增强提示（Reasoning-augmented）——均不需要微调**

- **Chain-of-Thought（CoT，思维链）**：让模型先输出中间推理步骤再给答案，提升复杂推理表现
- **Self-Consistency（自洽性）**：同一问题多次采样（调高 temperature 让路径不同），对最终答案多数投票。代价是 API 调用次数翻倍。适合有唯一答案的数学/逻辑题
- **ReAct**：让模型"边想边查"——循环执行 Thought（思考缺什么）→ Action（决定调哪个工具）→ Observation（系统执行查询并返回结果），直到信息足够给出答案。需要外部工具配合，不是纯 API 调用能自动完成的
- **提示注入**（Prompt Injection）：安全对抗概念，攻击者嵌入恶意指令劫持模型行为，部署时需防范

### 5. API 服务的能力边界（OpenAI / DeepSeek / GLM 等在线 API）

| 能做什么 | 不能做什么 |
|---|---|
| Prompt Design / Engineering | 真正的 Prompt Tuning（需注入软提示向量） |
| 零样本/少样本提示、CoT、Self-Consistency | Prefix Tuning |
| 结构化输出参数、低温度采样 | 复现 IAG 原论文完整方案（IAG-Student 需训练归纳器）* |
| 构建 RAG（厂商多提供兼容 Embedding 接口） | 访问模型权重与训练流程 |
| 实现 IAG 的简化版（Prompt 让模型生成归纳知识辅助回答） | — |
| 调用厂商微调 API（如有，本质是改权重） | — |

> \* IAG 为本组在研/调研中的特定论文方法，外部读者可跳过这两行。

### 6. 产品落地优先级

目标：每次按格式返回正确结果。按顺序做，前一步不够再上下一步：

1. **启用 API 结构化输出参数**（如支持）
2. **配低 temperature**
3. **系统消息写死格式约束**
4. **应用层加校验重试**（兜底保障）

前三步纯 API 调用可做，覆盖大部分格式稳定性问题；第四步需少量后端代码。**推理时工程 + 结构化输出 + 校验重试可覆盖绝大部分场景，不需要微调。**

### 7. Prompt Design 怎么做：直接用现成标准

前人已经给出成熟方案，**不自创提示设计的维度**。写 prompt 时按任务类型直接采用以下两个标准（全文见本文第二、三章）：

- **CO-STAR**：六要素 C 背景 / O 目标 / S 风格 / T 语调 / A 受众 / R 响应。适合内容创作类、输出面向特定受众的任务。
- **Anthropic 官方最佳实践**：8 条技巧——清晰直接 / 示例 / CoT / XML 标签 / 角色 / 预填充 / 链式提示 / 长上下文。适合 API 调用、输出被程序消费的工程场景。

| 场景 | 用哪个 |
|---|---|
| 内容创作、文案、面向特定受众的输出 | CO-STAR |
| API 工程调用，输出被下游程序消费 | Anthropic 清单（核心三件：XML 标签隔离 + 示例 + 显式输出格式） |
| 复杂工程 prompt | 并用：CO-STAR 定"要哪些要素"，Anthropic 定"怎么组织"（system prompt 角色、XML 分隔、示例数量） |

### 8. 一句话记忆

- Prompt Design = 写给人看的提示词；Prompt Tuning = 训给机器用的提示向量
- Self-Consistency = 闭卷考多遍取平均分；ReAct = 开卷考，允许翻书查资料
- 推理增强提示不需要微调；微调是独立路线，**不是起点**
- RAG 随便建；IAG 可借思路优化 Prompt，但完整版需自部署开源模型

## 二、CO-STAR 框架（中文版）

> 来源：GovTech 新加坡数据科学团队提出；Sheila Teo 以此框架赢得 **2023 年新加坡首届 GPT-4 提示工程大赛冠军**。
> 官方 playbook：https://go.gov.sg/promptengineering-playbook
> 作者原文：Sheila Teo, *How I Won Singapore's GPT-4 Prompt Engineering Competition*（Towards Data Science）
> 本篇为忠实译介，未做汇总改写。

### 框架定义

CO-STAR 把一条结构化 prompt 拆成六个要素：

| 字母 | 要素 | 英文 | 回答的问题 |
|---|---|---|---|
| **C** | 背景 | Context | 任务发生的背景信息是什么？ |
| **O** | 目标 | Objective | 你要模型输出什么？ |
| **S** | 风格 | Style | 按什么写作风格来写？ |
| **T** | 语调 | Tone | 输出的情感态度是什么？ |
| **A** | 受众 | Audience | 内容是写给谁看的？ |
| **R** | 响应 | Response | 输出格式是什么？ |

### 各要素说明

**C · Context（背景）**
提供任务所需的背景信息：你是什么角色、公司/产品情况、此前发生了什么、模型需要哪些领域知识。背景是其余所有要素的地基——同一句话在不同背景下含义完全不同。

**O · Objective（目标）**
明确说明你要模型做什么、期望输出什么效果。要具体到"意图"层面：不是"回答用户问题"，而是"帮用户在最短时间内解决问题"。

**S · Style（风格）**
指定写作风格，让模型模仿某个具体参照物：鲁迅风格、麦肯锡顾问风格、Apple 文案风格。风格是区分"泛泛输出"与"特定输出"的关键。

**T · Tone（语调）**
设定情感与态度：正式/随意、幽默/严肃、说服性/激励性。语调决定内容"读起来的感觉"。

**A · Audience（受众）**
说明输出是给谁看的：受众的身份、专业水平、关注点。受众越具体，模型的用词、举例、深度校准越准。

**R · Response（响应格式）**
指定输出格式：纯文本 / Markdown / JSON / 表格；长度；结构（是否编号、是否含小标题）。工程场景中这一项直接决定输出能否被程序消费。

### 完整示例（译自原作）

> **# 背景（CONTEXT）#** 我想推广公司的新产品。公司名为 Alpha，新产品名为 Beta，是一款新型超快速吹风机。
> **# 目标（OBJECTIVE）#** 帮我创建一条 Facebook 帖子，目的是吸引人们点击产品链接购买。
> **# 风格（STYLE）#** 参照戴森等成功公司推广类似产品时的文案风格。
> **# 语调（TONE）#** 说服性。
> **# 受众（AUDIENCE）#** 我们公司在 Facebook 上的主要受众是老年人，请针对该群体选择护发产品时的典型关注点来定制帖子。
> **# 响应（RESPONSE）#** 保持 Facebook 帖子简洁而深具影响力。

### 配套技巧：分隔符

CO-STAR 原文配套建议用**分隔符**把各要素隔开：基础用 `###`，配 HTML/XML 标签（如 `<example>` 包示例）。分隔符让模型无歧义地区分"指令""背景""数据"各部分，是结构化 prompt 的通用基建。

### 适用边界

- **适合**：输出质量取决于风格、语调、受众、格式的任务——内容创作、营销文案、面向特定人群的沟通、系统提示词设计。
- **不必用**：简单事实问答，一条朴素提示即可；框架是指导而非模板，不适用的要素可以跳过。
- **与 CoT 的关系**：CO-STAR 管"输出成什么样"，CoT 管"怎么思考"，两者可以叠加使用。

## 三、Anthropic 官方提示工程最佳实践（中文版）

> 来源：Anthropic 官方文档 *Prompt engineering overview*（platform.claude.com/docs → Build with Claude → Prompt engineering）
> 本篇为官方技巧清单的中文编译，保留原文结构，未做汇总改写。

### 1. Be clear and direct（清晰直接）

像对待一个聪明但刚入职、缺乏上下文的新人一样写指令：

- 把任务、约束、期望结果在一句话里说全，不写"帮我看看"式模糊指令
- 想要什么格式就说什么格式（"输出 JSON，含 summary 和 risk_level 两个键"）
- 把上下文/文档放在指令**前**，用标记隔开
- 步骤有顺序要求时用编号列表逐条写
- 说不清"什么是好输出"时，描述"什么算坏输出"

### 2. Use examples (multishot prompting)（用示例）

示例是引导输出格式、语调、结构**最可靠**的方式：

- 3~5 个示例效果最好（few-shot / multishot）
- 示例要**相关**（贴近真实场景）、**多样**（覆盖边界情况）、**结构化**（用标签包裹，与指令区分）
- 示例比长篇描述指令更省 token、更难被误解

### 3. Let Claude think (chain of thought)（让模型思考）

复杂任务允许模型先写中间推理步骤再给答案：

- 对数学、逻辑、多步分析类任务显著提升表现
- 引导语："先在 \<thinking\> 标签内逐步思考，再在 \<answer\> 标签内给出最终答案"
- 思考过程会占输出 token，简单任务不要滥用

### 4. Use XML tags（用 XML 标签结构化）

当 prompt 混合了指令、背景、示例、待处理数据时，用 XML 标签包裹各类内容：

- 如 `<instructions>`、`<context>`、`<example>`、`<document>`
- 标签名称一致且描述性强；有层级时用嵌套（多份文档包在 `<documents>` 内）
- 官方明确推荐此法，它让模型无歧义地解析各部分边界

### 5. Give Claude a role（给角色）

在 system prompt 中设定角色，把模型行为聚焦到使用场景：

- "你是一名资深数据工程师"——角色约束输出视角、措辞水平和知识层次
- 角色放在 system prompt 而非正文，对行为的约束力更强

### 6. Prefill the response（预填充响应）

在 assistant 侧预置回复的开头几个词：

- 可以强制跳过客套前导、直接进入格式（预填 `{` 强制 JSON 开头）
- 也可用于控制输出起点、禁用特定开头方式

### 7. Chain prompts（链式提示）

把复杂任务拆成多次调用，前一步输出作为后一步输入：

- 每一步任务更窄、成功率更高，且可逐步检查
- 典型拆法：先"提取要点"再"按要点写作"；先"分类"再"按类回答"
- 适用于：任务有明确子结构、单次调用要同时做太多事、需要中间结果可审计

### 8. Long context tips（长上下文技巧）

把长文档放进 prompt 时：

- 文档放 prompt 顶部（开头），指令放底部——官方实测此顺序表现最好
- 要求引用来源段落（"答案必须引用文档中的具体段落"）可显著抑制胡编
- 多文档分别用标签包裹并编号，问答时要求先引用编号再作答

### 官方建议的通用工作流

1. 先用最朴素的一条提示跑通，建立基线
2. 按"清晰直接 → 示例 → XML 标签 → 角色"逐项加强，每次只改一处
3. 用官方 Prompt Improver / 评测集对比改前改后
4. 复杂任务拆链式调用；仍不够才考虑微调（见本文第一章的边界）
