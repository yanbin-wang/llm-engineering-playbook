# 01 · Prompt 工程与微调的边界

> 决策问题：目标"让模型每次按格式稳定返回正确结果"，应该动提示、动系统，还是动权重？

## 一、核心概念澄清

### 1. Prompt 相关术语

| 术语 | 英文 | 含义 |
|---|---|---|
| 提示工程 | Prompt Engineering | 系统性设计提示词与调用参数，让模型稳定、可重复、规模化地输出正确结果 |
| 提示设计 | Prompt Design | 侧重沟通与表达：写清指令、设定角色、明确格式。常与 Prompt Engineering 混用 |
| 提示微调 | Prompt Tuning | 改模型内部参数的技术：训练可学习的"软提示"向量，**不是人写的文字** |
| 前缀调优 | Prefix Tuning | Prompt Tuning 的近亲，在每层 Transformer 前加可训练前缀向量 |

**关键区分：**

> Prompt Design / Engineering 是**推理时工程**（模型权重不动）；
> Prompt Tuning / Prefix Tuning 是**参数高效微调**（改内部参数，需要模型权重访问权限）。

### 1.5 两条线的"怎么做"

上表只回答了"是什么"，这里补齐"怎么做"。

#### Prompt Design 怎么做（一份 Prompt 的构成要素）

写提示词 = 按需组装下面六个元素。前三个几乎是必备项，后三个按任务取用：

| 要素 | 回答的问题 | 说明 |
|---|---|---|
| **身份 / 角色** | "你是谁" | 给模型一个明确身份（如"你是资深数据工程师"），约束输出视角与措辞水平 |
| **指令（任务）** | "做什么" | 动词 + 对象 + 期望结果，一句话说清。模糊指令是输出翻车的头号原因 |
| **上下文 / 输入数据** | "基于什么" | 模型要处理的原料，用分隔符（`###`、` ``` `、XML 标签）与指令隔离，防止用户输入污染指令 |
| **示例**（可选） | "照什么样子做" | 0 个 = 零样本；1~3 个 = 少样本。反例往往比正例更能矫正行为 |
| **输出格式**（可选） | "交付成什么样" | 字段模板、JSON Schema、段落数与长度——让结果可直接被程序消费 |
| **约束**（可选） | "边界在哪" | 必须做什么 / 禁止做什么（长度、语言、不许编造等） |

> 元素怎么组合、改完怎么验证，属于具体项目里的操作；记住这张清单，写任何 prompt 前先过一遍"我漏了哪个要素"。

**这张表的依据（不是自创清单）**

| 来源 | 性质 | 与本表的对应 |
|---|---|---|
| **CO-STAR 框架**（GovTech 新加坡数据科学团队；Sheila Teo 以此获 2023 首届 GPT-4 提示工程大赛冠军，官方 playbook 见 go.gov.sg/promptengineering-playbook） | 业界结构化提示框架，六要素：Context / Objective / Style / Tone / Audience / Response | Objective≈指令，Context≈上下文，Audience≈身份，Response≈输出格式；Style/Tone 是内容创作的细分，工程场景并入"身份+约束" |
| **Anthropic 官方提示最佳实践** | 厂商工程标准：role（系统提示）、context、3~5 个 multishot 示例、XML 标签隔离、显式输出格式与约束 | 与本表逐项对应；"1~3 个示例"一类数字的出处即此类官方建议 |
| **White et al., 2023,《A Prompt Pattern Catalog to Enhance Prompt Engineering with ChatGPT》**（arXiv:2302.11382） | 学术侧：将 prompt 模式当设计模式编目（persona、template、output automater 等） | 学术界尚无钦定的元素清单，但 pattern catalog 支撑了这些构件的成立 |

一句话：**本表 = CO-STAR + 厂商官方最佳实践在工程场景下的压缩**，不是发明；学术侧可作延伸阅读。

#### Prompt Tuning 怎么做（机制，理解边界即可）

- **冻结全部模型权重**，只训练一组**连续向量**（soft prompt）：在输入层（Prefix Tuning 则在每层 Transformer 前）拼接可训练向量，与文字 prompt 一起送入模型。
- 训练数据就是（输入 → 期望输出）对，梯度反传只更新这些向量，模型本体不动。
- 产物是**一组数值向量**，不是文字：人读不了、改不了，也基本不能跨模型迁移。
- 前提：必须能访问模型内部计算（自部署开源模型）。在线 API 给不了这个入口——这就是它在工程实践里出场率远低于 Prompt Design 的原因。

### 2. 微调（Fine-tuning）

用数据继续训练模型、修改模型权重，让模型"内化"格式或领域知识。与推理时工程是**两条独立路线**，不是同一件事的两个阶段。

## 二、两条技术路线

### 路线一：推理时工程（Inference-time Engineering）——不改权重

绝大多数产品的主路线。又分两层：

#### A. 纯提示层（Prompt-level，纯 API 调用可实现）

- 系统消息硬性约束输出格式（用分隔符隔离指令与内容）
- **零样本提示**（Zero-shot）：只给指令，不给示例
- **少样本提示**（Few-shot）：在 prompt 里给 1~3 个"输入→期望输出"示例，让模型模仿
- 低 temperature / top_p，降低随机性
- API 结构化输出参数（`response_format` 设为 `json_object` 或 JSON Schema），从解码层杜绝格式错误
- 分步拆解、链式调用：把复杂任务拆成多次 API 调用，每次任务更窄

#### B. 系统层（System-level，需 API 外基础设施）

- **输出校验 + 自动重试**：应用层用 JSON Schema / 正则校验，不合规就重调并把错误反馈给模型
- **RAG**（检索增强生成）：先检索相关资料再让模型回答，减少胡编、提升事实准确率
- **上下文工程**：向量库、文档处理、查询重写、状态管理
- **Function Calling / 工具调用**：让模型调函数查真实数据，服务端需实现函数端点

### 路线二：微调（Fine-tuning）——改权重

适用场景（**不是起点，是升级选项**）：

1. 格式极复杂，结构化输出参数搞不定
2. 领域术语/风格要求高，提示里塞示例太占 token
3. 延迟敏感，需要缩短提示
4. 厂商提供微调 API 且成本可接受

## 三、Prompt 工程内部的方法论

### 1. 按示例数量分

- **零样本**（Zero-shot）：不给示例，只写指令
- **少样本**（Few-shot / In-Context Learning）：在 prompt 里给示例让模型模仿。纯文本操作，成本最低

### 2. 推理增强提示（Reasoning-augmented）——均不需要微调

- **Chain-of-Thought（CoT，思维链）**：让模型先输出中间推理步骤再给答案，提升复杂推理表现
- **Self-Consistency（自洽性）**：同一问题多次采样（调高 temperature 让路径不同），对最终答案多数投票。代价是 API 调用次数翻倍。适合有唯一答案的数学/逻辑题
- **ReAct**：让模型"边想边查"——循环执行 Thought（思考缺什么）→ Action（决定调哪个工具）→ Observation（系统执行查询并返回结果），直到信息足够给出答案。需要外部工具配合，不是纯 API 调用能自动完成的
- **提示注入**（Prompt Injection）：安全对抗概念，攻击者嵌入恶意指令劫持模型行为，部署时需防范

## 四、API 服务的能力边界（OpenAI / DeepSeek / GLM 等在线 API）

| 能做什么 | 不能做什么 |
|---|---|
| Prompt Design / Engineering | 真正的 Prompt Tuning（需注入软提示向量） |
| 零样本/少样本提示、CoT、Self-Consistency | Prefix Tuning |
| 结构化输出参数、低温度采样 | 复现 IAG 原论文完整方案（IAG-Student 需训练归纳器）* |
| 构建 RAG（厂商多提供兼容 Embedding 接口） | 访问模型权重与训练流程 |
| 实现 IAG 的简化版（Prompt 让模型生成归纳知识辅助回答） | — |
| 调用厂商微调 API（如有，本质是改权重） | — |

> \* IAG 为本组在研/调研中的特定论文方法，外部读者可跳过这两行。

## 五、产品落地优先级

目标：每次按格式返回正确结果。按顺序做，前一步不够再上下一步：

1. **启用 API 结构化输出参数**（如支持）
2. **配低 temperature**
3. **系统消息写死格式约束**
4. **应用层加校验重试**（兜底保障）

前三步纯 API 调用可做，覆盖大部分格式稳定性问题；第四步需少量后端代码。**推理时工程 + 结构化输出 + 校验重试可覆盖绝大部分场景，不需要微调。**

## 六、一句话记忆

- Prompt Design = 写给人看的提示词；Prompt Tuning = 训给机器用的提示向量
- Self-Consistency = 闭卷考多遍取平均分；ReAct = 开卷考，允许翻书查资料
- 推理增强提示不需要微调；微调是独立路线，**不是起点**
- RAG 随便建；IAG 可借思路优化 Prompt，但完整版需自部署开源模型
